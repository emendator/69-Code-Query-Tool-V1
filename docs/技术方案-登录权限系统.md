## 1. 技术选型补充

在现有技术栈（FastAPI + SQLAlchemy 2.0 + SQLite + React 18 + AntD 5 + Axios）基础上，认证相关新增：

| 用途 | 库 | 版本建议 | 说明 |
| ------ | ----- | --------- | ------ |
| 密码哈希 | `passlib[bcrypt]` | ≥1.7.4 | `CryptContext(schemes=["bcrypt"])`，自动加盐 |
| JWT 签发/校验 | `python-jose[cryptography]` | ≥3.3.0 | FastAPI 官方推荐，HS256 |
| 邮箱校验 | `email-validator` | ≥2.0 | Pydantic `EmailStr` 依赖 |
| 邀请码生成 | `secrets`（标准库） | - | `secrets.token_urlsafe` / 自定义字符集 |

> `python-multipart` 已有（导入功能），登录表单若用 OAuth2 表单方式也依赖它。

**前端**：不引入 react-router（与现状一致，用状态切换页面）；不引入额外 UI 库，全部使用 AntD 5 现成组件。

### 关键设计决策

1. **主库 / 公司库分离**：
   - 主库 `data/69code.db`：系统级数据（用户、公司、邀请码）；
   - 公司库 `data/company_{company_id}.db`：业务数据（69码等），**每个公司一个文件**，实现物理隔离；
   - 公司库懒创建：首次有该公司的账号访问时自动建库建表。

2. **鉴权依赖注入**：所有业务路由统一加 `Depends(get_current_user)`，从 `user.company_id` 解析公司库 Session，保证数据隔离是强制性的、代码不可绕过的。

3. **JWT 无状态**：登录签发 token（含 `sub=user_id, role, company_id, exp`）；每次请求校验 token + 数据库中的账号有效期（双保险，管理员延长/清除后立即生效）。

## 3. 认证流程设计

### 3.1 密码存储

```python
# backend/security.py
from passlib.context import CryptContext

pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")

def hash_password(p: str) -> str:
    return pwd_context.hash(p)

def verify_password(plain: str, hashed: str) -> bool:
    return pwd_context.verify(plain, hashed)
```

### 3.2 JWT

```python
# backend/security.py
import os
from datetime import datetime, timedelta
from jose import jwt

SECRET_KEY = os.getenv("JWT_SECRET_KEY")  # 必须注入，无默认回退值
ALGORITHM = "HS256"
ACCESS_TOKEN_EXPIRE_MINUTES = 60 * 12   # 12 小时，可配置

def create_access_token(user) -> str:
    payload = {
        "sub": str(user.id),
        "role": user.role,
        "company_id": user.company_id,
        "exp": datetime.utcnow() + timedelta(minutes=ACCESS_TOKEN_EXPIRE_MINUTES),
    }
    return jwt.encode(payload, SECRET_KEY, algorithm=ALGORITHM)

def decode_token(token: str) -> dict:
    return jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM])
```

> 生产环境（服务器部署）建议通过环境变量注入 `JWT_SECRET_KEY`；本地开发可用默认值并在文档中标注。

### 3.3 鉴权依赖

```python
# backend/deps.py (或并入 main.py)
oauth2_scheme = OAuth2PasswordBearer(tokenUrl="/api/auth/login")

def get_current_user(token: str = Depends(oauth2_scheme), db: Session = Depends(get_master_db)):
    payload = decode_token(token)                     # 失败 → 401
    user = get_user_by_id(db, int(payload["sub"]))    # 不存在/被删 → 401
    if user.is_expired():
        raise HTTPException(403, "账号有效期已到，请联系管理员")
    if user.status != "active":
        raise HTTPException(403, "账号已被禁用")
    return user

def get_current_admin(user = Depends(get_current_user)):
    if user.role not in ("super_admin", "admin"):
        raise HTTPException(403, "无权限")
    return user

def get_current_super_admin(user = Depends(get_current_user)):
    if user.role != "super_admin":
        raise HTTPException(403, "仅最高级管理员可操作")
    return user

def get_company_db(user = Depends(get_current_user)):
    return company_session_factory(user.company_id)   # 按公司路由
```

## 4. API 设计

统一响应格式沿用 `{success, data, message}`；业务接口统一前缀 `/api`。

### 4.1 认证 `/api/auth/*`

```
POST /api/auth/register/check-invite
     Body: { invite_code }
     → { success, data: { level: 1|2, company_name?: str } }
     说明: 注册前校验邀请码，返回级别（前端据此渲染公司选项：一级=创建/加入，二级=仅加入）

POST /api/auth/register
     Body: {
       username, password, email,
       invite_code,
       mode: "create" | "join",          # 管理员可二选一，用户强制 join
       company_name,
       company_db_password,
     }
     → { success, data: { user: {...}, token } }   # 注册成功直接登录

POST /api/auth/login
     Body: { username, password }
     → { success, data: { token, user: { id, username, role, company_name, expires_at, ... } } }
     → 账号到期: 200 { success:false, message:"账号有效期已到，请联系管理员" }

GET  /api/auth/me
     → { success, data: user(含公司名、角色、有效期、剩余天数) }

POST /api/auth/change-password            # 可选: 修改自己密码
     Body: { old_password, new_password }

PUT  /api/auth/company/password           # 管理员/超管修改本公司数据库密码
     Body: { old_db_password, new_db_password }
```

### 4.2 邀请码 `/api/invites/*`（super_admin / admin）

```
GET    /api/invites                # 我的邀请码列表(分页)
POST   /api/invites                # 分发: { level, expires_at?, account_expires_at? }
                                  # super_admin 可发 1/2 级; admin 仅可发 2 级(后端强校验)
DELETE /api/invites/{id}           # 撤销未使用的邀请码
```

### 4.3 用户管理 `/api/users/*`（super_admin / admin）

```
GET    /api/users?page=&page_size=&search=&role=&status=
       → { items: [ { id, username, role, company_name, email,
                      created_at, last_login_at, expires_at, status } ], total }
       数据范围: super_admin=全部; admin=本账号 + 自己邀请的账号(后端按 invited_by 过滤)

PUT    /api/users/{id}/extend      # 延长有效期: { expires_at } 或 { days }
DELETE /api/users/{id}             # 清除账号; super_admin 删 admin 时级联删其邀请的 user
       → 级联时返回 { deleted_count }
```

### 4.4 业务接口改造（鉴权 + 公司库路由）

现有所有业务路由增加鉴权与公司库：

| 现有路由 | 改造方式 |
| --------- | --------- |
| `/api/query/*` | `Depends(get_current_user)` + `Depends(get_company_db)` |
| `/api/data/*` | 同上 |
| `/api/import/*` | 同上（上传临时文件建议按公司子目录隔离） |
| `/api/config/*` | 同上（列配置存公司库） |

> 导入临时文件目录：`data/upload/company_{id}/` 隔离，避免跨公司文件名冲突。

## 5. 公司库（多库）实现

### 5.1 引擎注册表

```python
# backend/database.py 增加
COMPANY_DATA_DIR = os.path.join(DATA_DIR, "companies")   # data/companies/
_company_engines: dict[int, Engine] = {}

def get_company_engine(company_id: int) -> Engine:
    if company_id not in _company_engines:
        os.makedirs(COMPANY_DATA_DIR, exist_ok=True)
        path = os.path.join(COMPANY_DATA_DIR, f"company_{company_id}.db")
        engine = create_engine(f"sqlite:///{path}",
                               connect_args={"check_same_thread": False})
        _company_engines[company_id] = engine
        Base.metadata.create_all(bind=engine)   # 懒建表(幂等)
    return _company_engines[company_id]

def get_company_db(company_id: int):
    engine = get_company_engine(company_id)
    Session = sessionmaker(bind=engine)
    db = Session()
    try:
        yield db
    finally:
        db.close()
```

> 注意：`Base.metadata.create_all` 对主库与公司库共用同一套 `Base`；主库只注册系统表模型，公司库只注册业务表模型——可通过**分离 Model 基类**（`MasterBase` 用于系统表，`BizBase` 用于业务表）实现，避免主库误建业务表。见《数据库设计》第 7 节。

### 5.2 隔离保障

- 业务层只能拿到 `get_company_db` 提供的 Session，无法触碰其他公司数据；
- 主库 Session 与公司库 Session 类型分离（不同的 sessionmaker），避免混淆；
- 清除公司时（删除公司最后账号等场景）不物理删除 db 文件（数据保全），仅逻辑处理。

## 6. 前端架构

### 6.1 登录态管理（AuthContext）

```tsx
// frontend/src/context/AuthContext.tsx
interface AuthState {
  token: string | null
  user: UserInfo | null
  login(username, password): Promise<void>
  logout(): void
  refreshMe(): Promise<void>
}
```

- `token` / `user` 持久化到 `localStorage`（key 如 `69code_token` / `69code_user`）；
- Axios 请求拦截器统一注入 `Authorization: Bearer <token>`；
- 响应拦截器：401 → 清除登录态 → 跳转登录页。

### 6.2 页面结构

```
App.tsx
├── 无 token → 认证页 (LoginPage / RegisterPage 切换)
└── 有 token → 主界面 Layout
    ├── 顶栏: 系统名 | 用户信息(用户名/角色/公司/剩余有效期) | 退出登录
    ├── 侧栏菜单(按角色过滤): 69码查询 / 数据管理 / 列配置 / 用户管理(admin+)
    └── 内容区: QueryPage / DataManagePage / ConfigPage / UserManagePage
```

### 6.3 登录/注册页 UI（美观大气简约）

- 居中卡片（宽约 400px），圆角 12px、卡片阴影、浅色渐变背景（如 `linear-gradient(135deg, #1677ff 0%, #69b1ff 100%)` 顶部点缀）；
- 卡片内：Logo/标题「69码查询器」+ 副标题、Form 表单（AntD `Form` + `Input.Password`）；
- 登录页：用户名、密码、登录按钮、底部「没有账号？去注册」；
- 注册页：用户名、密码、确认密码、邮箱、邀请码；校验邀请码后动态显示公司区域：
  - 一级码 → Radio：「创建新公司 / 加入公司」，创建模式显示「公司名称（填写后不可修改）」「设置公司数据库密码」；
  - 二级码 → 仅「加入公司」：公司名称 + 公司数据库密码；
- 表单校验：必填、密码 ≥ 6、确认密码一致、邮箱格式、用户名规则（字母数字下划线，3-20 位）。

### 6.4 用户管理页（UserManagePage）

两个 Tab：

- **邀请码管理**：Table 展示；「分发新邀请码」Modal（级别按角色过滤、有效期、账号默认有效期）；撤销操作；
- **账号管理**：Table（用户名/角色/公司/邮箱/注册时间/最后登录/有效期/状态）；操作：延长有效期（Modal 选新到期日或+N天）、清除（Modal 二次确认，级联时显示将连带删除数量）；状态 Tag（正常/已过期/已禁用）。

### 6.5 到期提醒

- 登录成功后 `me` 返回剩余天数；主界面顶栏显示「有效期至 2026-08-20（剩 N 天）」；
- 剩余 ≤ 7 天时 Alert 醒目提示；
- 已到期被拒登录时，登录页展示后端返回的明确错误信息。

## 7. 安全设计

| 项 | 方案 |
| ---- | ------ |
| 密码 | bcrypt 哈希（passlib），禁止明文入库/日志 |
| JWT 密钥 | 环境变量 `JWT_SECRET_KEY`，生产必配 |
| Token 过期 | 12h 可配置；到期后需重新登录 |
| 账号状态校验 | 每次请求都查库校验 `status` + `expires_at`（管理员操作即时生效） |
| 邀请码 | 高熵随机；一次一码；过期/撤销；防枚举（校验接口不暴露码是否存在以外的信息，统一文案） |
| 注册防滥用 | 用户名/邮箱唯一约束；邀请码为门槛 |
| 数据隔离 | 公司库物理分离 + 依赖注入强制路由，业务代码无公司参数可传 |
| 输入校验 | Pydantic 全量校验；邮箱 `EmailStr`；密码长度 ≥ 6 |
| 级联删除 | 事务内执行，先统计后删除，二次确认 |
| super_admin 保护 | 删除/降级接口显式拒绝 super_admin 自身账号 |

## 8. 数据流示例

### 8.1 用户注册（管理员，创建公司）

```
前端: 输入 用户名/密码/邮箱/一级邀请码/创建公司
  → POST /api/auth/register/check-invite  校验邀请码(level=1)
  → 前端渲染「创建新公司」表单
  → POST /api/auth/register
     后端: 校验邀请码 → 校验用户名/邮箱唯一
           → 创建 companies 记录 + 生成 company_{id}.db 并建表
           → 创建 user(role=admin, invited_by=码分发者, expires_at=码的account_expires_at)
           → 邀请码置 used
           → 签发 token → 返回
  → 前端保存 token，进入主界面
```

### 8.2 用户登录后查询

```
前端: token → POST /api/query/batch
后端: get_current_user(校验token+有效期)
      → get_company_db(user.company_id) → 查公司库 products
      → 返回该公司数据
```

### 8.3 超管删除管理员

```
DELETE /api/users/5 (role=admin)
后端: 校验为 super_admin → 统计 invited_by=5 且 role=user 的账号数
      → 事务: 删除这些 user → 删除 admin → 返回 deleted_count
前端: 二次确认(展示将删除 N 个关联用户) → 刷新列表
```
